# Архитектура RPG Adventure

> Технические границы для развития после 1.0. Нормативный scope игры остаётся в [PROJECT_SPEC.md](PROJECT_SPEC.md); этот документ не расширяет релиз 1.0.

## Принципы

- Ядро не зависит от конкретного контента и UI.
- Контент хранится декларативно и читается через каталоги.
- Игровые системы имеют явный публичный API.
- Формат сохранения версионируется последовательными миграциями.
- Каждое расширение сопровождается тестами и проверкой старых сохранений.
- Произвольный исполняемый код не загружается из контентных данных.

## Слои

| Слой | Ответственность | Запрещённая зависимость |
|---|---|---|
| `js/core` | состояние, Storage, миграции, реестры | UI |
| `js/data` | декларативные определения и lookup API | DOM, UI, systems |
| `js/systems` | правила боя, квестов, крафта, NG+ | конкретные экраны |
| `js/entities` | игровые сущности и поведение | разметка интерфейса |
| `js/ui` | отображение и ввод | бизнес-правила |
| `tests` | unit/integration/regression | — |

## Реестр контента

`js/core/contentRegistry.js` экспортирует `createContentRegistry({ kind, validate })`.

- ID: уникальный lowercase snake_case.
- `register(entry)` и `registerMany(entries)` добавляют определения.
- `registerMany` сначала проверяет весь пакет: при ошибке ничего не добавляется.
- Дубликаты и невалидные записи приводят к явной ошибке.
- `get/has/list/size` — стабильный API чтения.
- Реестр не клонирует записи. Не храните в определениях изменяемое состояние прохождения.

Встроенные каталоги: `ENEMY_REGISTRY`, `ITEM_REGISTRY`, `QUEST_REGISTRY`, `ACHIEVEMENT_REGISTRY`, `LOCATION_REGISTRY`. `js/data/validateContent.js` проверяет перекрёстные ссылки этапов на врагов и наград регионов/квестов на предметы. Старые массивы/объекты и функции lookup сохранены для обратной совместимости.

Реестры регистрируют данные, а не исполняемый код. Динамические импорты и внешние плагины в игре не поддерживаются.

## Версии сохранений

- Текущий envelope: `CURRENT_SAVE_VERSION = 2`.
- Новые сохранения записывают `schemaVersion`.
- Сохранение без версии считается версией 0 и проходит последовательные миграции 0 → 1 → 2.
- Версия выше поддерживаемой отклоняется, а не понижается; перед заменой повреждённого/будущего формата сохраняется recovery-копия.
- Миграции envelope отделены от нормализации полей игрока.
- Версия 2 добавляет валидируемые per-location snapshots `player.dungeonProgress`: этап, побеждённые обычные враги и состояние уже принятых решений экспедиции.
- При добавлении новой версии создаётся последовательная миграция N → N+1; существующие миграции не переписываются задним числом.

## Направление зависимостей

- `core` не импортирует `ui`.
- `data` не импортирует `systems` или `ui`.
- `systems` использует публичные API `core/data`, не манипулирует DOM.
- `ui` вызывает публичные функции систем.
- Межсистемное взаимодействие оформляется публичными методами/событиями. Массовое переписывание существующего кода не является целью.

## Политика расширения

Новые content packs сначала добавляются в исходный код, проходят registry validation и CI. Новая gameplay-система получает отдельный модуль, публичный API, миграцию (если нужна) и тесты. Изменения scope 1.0 проходят Change Request; после релиза — отдельный backlog.
